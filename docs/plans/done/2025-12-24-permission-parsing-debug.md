# Debug: Permission Parsing Issues

## Что тестируем

Background permission poller иногда некорректно парсит контент permission prompt.

**Симптомы:**
- Отсутствуют dashed разделители (╌╌╌ или "- - -")
- Подхватывается лишний текст из предыдущих сообщений
- Контент обрезается или пустой

## Что хотим понять

1. Как выглядит raw tmux capture в момент детекта permission
2. Почему `parse_screen()` не находит контент между разделителями
3. Какие паттерны в tmux output ломают парсинг

## Данные

| Файл | Содержимое |
|------|------------|
| `/tmp/poller-debug.log` | Лог state machine transitions + parsed fields |
| `/tmp/poller-screen-raw.txt` | Raw tmux capture в момент IDLE→DEBOUNCING |

## Что сравнивать

1. **Raw screen** vs **parsed fields**:
   - Есть ли в raw разделители `─────` и `╌╌╌` (или `- - -`)?
   - Что между ними?
   - Совпадает ли с `description`, `content`, `question` в логе?

2. **Успешные vs неуспешные кейсы**:
   - Когда контент парсится правильно — как выглядит raw?
   - Когда ломается — что отличается?

## Как воспроизвести

1. Триггернуть permission (Edit/Bash с подтверждением)
2. Посмотреть что пришло в Telegram
3. Сравнить с `/tmp/poller-screen-raw.txt` и `/tmp/poller-debug.log`

## Баг: разделители внутри diff (2025-12-24 07:44)

### Проблема

Когда редактируемый файл содержит примеры разделителей (как этот MD файл), парсер находит их **внутри diff** вместо реальных разделителей permission prompt.

### Raw capture

```
 62 +───────────────────────────────────────   ← строка из MD в diff
 63 + Edit file src/telegram_bridge/__init__.py
 64 +╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌   ← строка из MD в diff
 ...
╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌   ← РЕАЛЬНЫЙ разделитель
 Do you want to make this edit to ...?
```

### Лог

```
description=+─────...           ← мусор из diff
content=+╌╌╌╌╌                  ← мусор из diff
question=68 + Do you want...    ← номер строки из diff
```

### Гипотезы фикса

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **1. Искать с конца** | Простой, permission всегда внизу | Нужно переписать логику поиска |
| **2. Искать только в последних N строках** | Ещё проще — slice screen[-30:] | Может обрезать длинный diff |
| **3. Искать по уникальному паттерну** | Надёжнее | Сложнее, паттерн может измениться |
| **4. Искать `❯` + options как якорь** | Options всегда есть | Потом парсить вверх — сложно |

**Рекомендация:** Вариант 2 — взять последние 30-40 строк screen перед парсингом. Permission prompt занимает ~15-20 строк максимум.

```python
# В parse_screen()
lines = screen.split('\n')
# Берём только нижнюю часть где permission prompt
lines = lines[-40:] if len(lines) > 40 else lines
```

Это отсечёт весь предыдущий вывод (включая diff с разделителями) и оставит только актуальный permission prompt.

## Баг: question из предыдущего сообщения (2025-12-24 07:46)

### Проблема

Парсер нашёл `?` в предыдущем сообщении Claude вместо реального question.

### Лог

```
question=Хочешь сейчас пофиксить screen.py или добавить в б...
```

Реальный question: `Do you want to make this edit to ...?`

### Причина

Та же — парсер ищет первый `?` сверху вниз, находит его в предыдущем выводе.

### Подтверждение

Вариант 2 (slice последних 40 строк) решит и эту проблему.

## Решение (2025-12-24 12:00)

### Итоговый подход

Вместо slice и отдельных парсеров для description/content/question — **упрощённая логика**:

1. Найти последний solid separator `────`
2. Проверить что после него нет `●` (иначе это не permission prompt)
3. Взять всё до `❯` как `body` (единый текст)
4. Заменить `╌╌╌` на `- - -` для красивости
5. Options парсить от `❯`

### Почему это лучше

| Было | Стало |
|------|-------|
| 4 парсера (description, content, question, options) | 1 парсер (body + options) |
| Slice 40 строк (может отрезать длинный diff) | Ищем от `────` (не теряем контент) |
| Проверка `Do you want` (не все вопросы) | Любой текст до `❯` |
| `❯` в коде триггерит false positive | `●` после `────` = не permission |

### Ключевой инсайт

Внутри permission prompt **нет `●`**, а в обычном выводе Claude — есть. Это надёжный маркер.

### Статус

✅ **Пофикшено.** Все баги закрыты рефакторингом `screen.py`.

## Известные edge cases

### Edit файла с `❯` внутри

Если редактируемый файл содержит `❯` в тексте (как этот MD):
- Debug лог показывает `❯ found but no permission!`
- Это false positive — `❯` из текста файла, не из permission prompt
- Парсер корректно возвращает Idle (находит `●` после separator)

Не требует фикса — парсер работает правильно.

## Баг: длинные prompts обрезаются (2025-12-24 13:00)

### Проблема

При длинном diff или multi-question prompt, `❯` оказывается за пределами видимой части tmux окна. Парсер не находит options → возвращает Idle.

### Причина

`capture_pane()` использует `tmux capture-pane -p` — захватывает только видимую часть (59 строк). Если prompt длиннее — `❯` не попадает в capture.

### Симптомы

- Большой Edit diff не показывается в Telegram
- Лог: `DEBUG: ❯ found but no permission! parsed=Idle`

### Решение

Добавить `-S -` для захвата scrollback buffer:
```python
f"tmux capture-pane -t {session} -p -S -"
```

## Баг: `●` в тексте файла (2025-12-24 13:00)

### Проблема

Если редактируемый файл содержит `●` в тексте, парсер находит его в diff и возвращает Idle.

### Пример

```
────────────────────────────
 Edit file docs/debug.md
╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌
+ ● Bash(...)      ← в тексте файла
╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌
 ❯ 1. Yes
```

Текущая проверка `"●" in line` находит `●` → Idle.

### Решение

Проверять что `●` в начале строки (реальные tool markers):
```python
# Было
if "●" in line:

# Стало
if line.lstrip().startswith("●"):
```

В diff строки начинаются с `+`/`-`/номера, не с `●`.

## Баг: multi-question не показывается (2025-12-24 13:00)

### Проблема

При AskUserQuestion с 2+ вопросами:
1. Первый вопрос отправляется в Telegram ✓
2. Второй+ вопросы НЕ отправляются ✗
3. Финальный Submit НЕ отправляется ✗

### Причина

В SHOWING state поллер только обновляет клавиатуру при смене options:
```python
elif parsed.options != last_options:
    kb = permission_keyboard(parsed.options)
    await kb_msg.edit_reply_markup(reply_markup=kb)
```

Body (текст вопроса) не проверяется и не отправляется.

### Решение

Отслеживать `body` и при его смене отправлять новое сообщение:
```python
elif parsed.options != last_options or parsed.body != last_body:
    # Удалить старые сообщения
    # Отправить новый body + options
    last_body = parsed.body
```
